IMS Update Server

Administer separate Client and Global release folders through the IMS API-authorized update service. Workstation authorization is central and does not require separate updater credentials for each company.

Authorization and administrator responsibilities

IMS API checks an existing approved Global workstation record and its matching hardware fingerprint before issuing a short-lived, product-specific update ticket. Every file request checks the ticket and the current workstation approval/fingerprint again. Unknown, pending, blocked or revoked workstations cannot download. Update access does not require a user login, company selection or company database credentials.

Review the workstation roster against independently verified device inventory before enabling updates. Registration is not approval. Use IMS Global → System → Workstations for normal administration and the first-workstation procedure for a new installation.

Protect the download boundaryDo not expose update folders through anonymous IIS mappings, aliases or direct file URLs. Workstation IDs and fingerprints are self-reported, not cryptographic proof of a physical device. Protect approved identity details and update tickets, and promptly block devices whose approval is withdrawn.

Prepare independent release sources

  • Choose an existing absolute local folder or UNC share separately for Client and Global. Keep sources outside all IIS physical directories and aliases, outside protected configuration directories, and free of junctions or symbolic links that bypass authorization.
  • Client source must contain Update.exe and IMS_Update.zip, with the approved release's corresponding system-version metadata.
  • Global source must contain the approved complete distribution named Global_Update.zip. The ZIP must contain exactly one valid IMS_Global.dll assembly with a published version. A release-directory prefix is accepted; missing, duplicate or invalid assembly metadata is rejected.
  • Grant the API application-pool identity read access to local source files. For UNC sources, verify both share and NTFS read permissions for the actual API server identity or a dedicated read-only network account. Successful access by an interactive administrator does not prove API access.
  • Prepare and publish complete releases through the approved release process. Setup does not create, copy, rename or edit packages or broaden source permissions.

Setup inspects Global_Update.zip without executing or extracting its contents, detects the IMS_Global.dll assembly version and displays it for review. You do not enter a Global ZIP filename or version manually. Where the Global database provides a central Global version, the approved central version, configured version and archive metadata must agree on every node. Configuration does not overwrite restored version data or migrate the database.

Configure the authorized service

  1. Confirm that the intended API is installed, its trusted HTTPS binding works and its update protocol is supported. On a new installation, optional update configuration follows API health verification. On an existing installation, run Setup.exe --configure-updates or choose Configure IMS Update Server only (existing API installation) under Installation mode.
  2. Complete prerequisite checks and any separately approved restart before entering secrets. Supply Existing IMS API IIS site name, Existing API HTTPS DNS hostname (without scheme) and Existing API HTTPS port when prompted.
  3. Review any existing update configuration and identified installer-owned static mappings. Approve replacement only after confirming their ownership and that no unmigrated workstation depends on their removal. Foreign/shared IIS conflicts or an incomplete alias inspection require operator resolution.
  4. Confirm that the workstation roster has been reviewed and that separate approved legacy delivery remains available for clients still requiring it.
  5. Enter Existing /update/client source directory (local drive or UNC share) and the equivalent Global directory. For UNC access, choose Existing API Windows identity or Separate read-only network account. Enter the latter account's credentials only in the masked installer prompts. Confirm read access and absence of public aliases.
  6. Review the automatically detected Global assembly version. If it is wrong or cannot be read, correct the approved archive/source access before continuing.
  7. At Server-only update-ticket signing key, generate a new key for a new single-node configuration or import the existing shared key for another node. For an existing configuration, Preserve the existing update-ticket key is the default. Keep any one-time displayed key in approved secure custody.
  8. Review both HTTPS routes and source directories, then approve Apply this API-authorized IMS Update Server configuration?.
  9. Wait for protocol checks, anonymous GET/HEAD denial and API health verification. Then perform the authorized-workstation and source-access checks below; Setup does not approve a test workstation for you.

Protected configuration

Source locations, optional share credentials, Global release metadata and the ticket-signing key stay on the API server in %ProgramData%\IMS\Updates\update-sources.bin, protected for that Windows machine with restricted access. They are not company/POS settings or values to send to clients. The API runtime-secret store, database roles and company/vault encryption keys are separate.

Update tickets last 120 seconds and are bound to the product, workstation ID and fingerprint. File requests use an Authorization bearer header, not a token in the URL. A ticket-signing key is server-only; changing it invalidates outstanding tickets without changing database or vault keys. Do not put keys, tickets or share passwords in process arguments, plaintext configuration, reports or logs.

Single-server and two-node configuration

For one API server, configure both sources and the local protected settings on that server. For two load-balanced API nodes, configure each node independently with the same ticket-signing key, Global workstation registry and approved release metadata/content. Each node may use its own local directory or an appropriately authorized share.

Verify share and NTFS access on each node, then confirm a ticket issued by either node can download the correct files through the other. Compare release bytes and content types. Never copy a machine-bound protected file between nodes. Coordinate explicit key rotation across both nodes and keep the shared key in approved secure custody.

Change an existing configuration

Use the update-only installer path to change directories, account access or release configuration. Review the identified existing configuration and approve the replacement. Supply required share credentials again; saved passwords are not revealed. Preserve the existing signing key for a path-only change unless a coordinated rotation is intended.

The API must already support the authorized update protocol. If it does not, follow the approved API binary-maintenance procedure before configuring updates; Fresh Installation and Disaster Recovery are not binary-refresh commands. Keep existing application settings, HTTPS bindings and runtime secrets under that maintenance procedure.

Source reconfiguration does not require an API pool recycle. A failed update operation does not undo completed API/database work. Correct the reported path, permission or mapping issue and retry --configure-updates; do not regenerate database keys or remove the runtime store. A failed migration must not be resolved by restoring an anonymous download bypass.

Existing Client and Global installations

The authorized service requires compatible update-capable application releases. An older Client using company updater settings cannot adopt the protocol by changing its URL alone. Distribute the approved compatible Client release through its existing IMS Updater 8.0.3 delivery and retain separate legacy delivery, settings and credentials until the workstation inventory confirms migration. Do not raise login minimum versions before the required upgrade path is available.

IMS Client 9.4.8 uses its existing update workflow after company connection. Keep its company updater configuration and approved legacy delivery operational. The authorized server endpoints do not by themselves change that installed Client workflow.

Installing IMS Global 1.7.0 remains an administrator-controlled full-distribution procedure. It does not provide automatic software replacement through this service. Server configuration alone does not install an update component into Client or Global.

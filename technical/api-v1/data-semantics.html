IMS Business API v1

Data Semantics

Source-verified API field shapes and selected business calculations from the packaged IMS Global company-view contract. Confirm deployed schema equivalence before using these definitions for reconciliation.

Evidence boundary for calculations

Packaged source, not deployed schema verificationThe API reads company api_v1.* views. Selected formulas on this page are verified against IMS_Global/Sql/API_v1_Company_Contract.sql at the pinned IMS Global 1.4.0 source. This establishes the packaged calculation, not that every deployed database uses it. Deployed DDL equivalence, source-data integrity, upstream discount allocation and promotion-value units remain unverified.

The sales DTO confirms customer/loyalty IDs without customer name, phone or email fields. Coupon DTOs omit raw coupon codes. These are response-shape observations, not guarantees about all data held in upstream systems.

Sales and returns

  • Sales transaction types are 51/52; return transaction types are 53/54.
  • quantity is the raw line quantity. netQuantity is zero for non-merchandise lines (itemType != 1); merchandise quantities are sign-reversed for return types 53/54. The view does not enforce positive input quantities.
  • grossSalesAmount uses quantity × price for merchandise and the stored total otherwise. netSalesAmount uses stored total minus disc2; cogsAmount uses quantity × item cost. These amounts are sign-reversed for types 53/54, so normal positive return values reduce sales totals.
  • discountPercent, discountAmount and invoiceDiscountAmount map the stored udisc_p, udisc and disc2 values. The view does not prove how upstream discount allocation was calculated.
  • isItemDiscounted and isInvoiceDiscounted identify those two discount mechanisms; isDiscounted is true when either applies.
  • salespersonId/salespersonName are line-level sales-associate references.
  • customerId and loyaltyCustomerId are separate identity namespaces. They may both be null, either may be present, or both may be present. The API does not expose customer phone/email/name as part of this sales linkage.

Purchases and landed cost

  • Transaction type 1 is Purchase; type 2 is Purchase Return. Signed cost/quantity fields reverse on returns.
  • lineForeignAmount is the raw line amount. foreignCostAmount, localCostAmount and landedCostAmount are signed business values.
  • The signed line total supplies foreign cost; local cost multiplies it by currancy_change and landed cost by costrate. landedExpenseAmount = landedCostAmount - localCostAmount. Type 2 reverses these signs.
  • Discount Earned is document-level. documentDiscountEarned is not allocated to purchase item rows and does not reduce line acquisition/landed cost.
  • Document-level totals repeat on each row of the same purchase. Do not sum those header fields across lines; deduplicate using the composite transaction-type, purchase-center and purchase-number identity (code, pcenter, bilno in the view join).

Inventory and movements

inventory is a current balance/valuation contract. Current valuation uses quantity × cost and quantity × sale price. For dated flow analysis use inventory/movements. Purchase movements include only state-2 documents with a receiving store; their landed unit cost is total × costrate ÷ quantity, with null for a zero denominator.

These are typical signs for normal positive source quantities, not positivity constraints. Adjustments retain their stored sign; depreciation is negated. Source data must be validated independently.

Transfers

A transfer exposes both sides: sourceMovementQty is −quantity and destinationMovementQty is +quantity. For a balanced transfer those movements cancel when aggregated across both stores.

Markdowns, promotions and coupons

  • markdownPercent is (1 - markdown price / original price) × 100, expressed in percentage points: 25 means 25%. It is null when the original price is missing or zero.
  • The packaged promotion view passes the stored so.get value through as getValue. Its units and interpretation for each promotionType are not established by this SQL alone; confirm the applicable business rule rather than treating every value as a percentage or amount.
  • Promotion relationship endpoints expose the stores/items/client categories/tiers/cashback stores attached to the promotion.
  • Discount-coupon endpoints expose event metadata and store eligibility. Raw coupon codes/prefixes are intentionally not exposed.

Data Semantics

Dates, signed quantities, amounts, cost and transaction meaning in Business API v1.

These calculations require the company API contract for the documented release. Sales responses include customer and loyalty IDs without customer name, phone or email; coupon responses omit raw coupon codes. The Partner Data guide defines its own cost-free price and availability contract.

Customer identity and enrichment

The Customers catalog is based on loyalty customers. Its id is the loyalty identifier, distinct from the ERP customer ID. Do not join it to sales customerId as if they were the same namespace.

phone concatenates the stored country code and mobile number. ERP enrichment uses exact telephone matching. Only exactly one active ERP match supplies customerCategory and discountPercent; zero or multiple active matches leave both fields null. Other nullable source values may also remain null. An actual discountPercent of 0 is different from missing enrichment; never replace null with zero.

Use the full catalog for initial synchronization or periodic reconciliation. The separate Customer Delta endpoint supplies subsequent changes using a captured baseline and revision. The catalog route itself has no date filters or push delivery. Each page request reads its count and rows in one repeatable-read transaction, but a multi-page export is not one database snapshot. Source changes between requests can affect the pages; reconcile only after the full download succeeds.

Financial-data permissions can set cost, acquisition and rent fields to null even where underlying business values exist. External transfer, adjustment and depreciation document totals are always null. Never replace a masked null with zero; use the per-resource field masking lists.

Sales and returns

  • Sales transaction types are 51/52; return transaction types are 53/54.
  • quantity is the raw line quantity. netQuantity is zero for non-merchandise lines (itemType != 1); merchandise quantities are sign-reversed for return types 53/54. The view does not enforce positive input quantities.
  • grossSalesAmount uses quantity × price for merchandise and the stored total otherwise. netSalesAmount uses the stored line amount minus the stored invoice-discount amount; cogsAmount uses quantity × item cost. These amounts are sign-reversed for types 53/54, so normal positive return values reduce sales totals.
  • discountPercent, discountAmount and invoiceDiscountAmount report the saved item discount percentage, item discount amount and invoice discount amount. Use these saved values rather than assuming invoice discounts were allocated using your own formula.
  • isItemDiscounted and isInvoiceDiscounted identify those two discount mechanisms; isDiscounted is true when either applies.
  • salespersonId/salespersonName are line-level sales-associate references.
  • customerId and loyaltyCustomerId are separate identity namespaces. They may both be null, either may be present, or both may be present. The API does not expose customer phone/email/name as part of this sales linkage.

Purchases and landed cost

  • Transaction type 1 is Purchase; type 2 is Purchase Return. Signed cost/quantity fields reverse on returns.
  • lineForeignAmount is the raw line amount. foreignCostAmount, localCostAmount and landedCostAmount are signed business values.
  • The signed line total supplies foreign cost; local cost multiplies it by exchangeRate and landed cost by costRate. landedExpenseAmount = landedCostAmount - localCostAmount. Type 2 reverses these signs.
  • Discount Earned is document-level. documentDiscountEarned is not allocated to purchase item rows and does not reduce line acquisition/landed cost.
  • Document-level totals repeat on each row of the same purchase. Do not sum those header fields across lines; deduplicate using the composite transaction-type, purchase-center and purchase-number identity.

Inventory and movements

inventory is a current balance/valuation contract. Current valuation uses quantity × cost and quantity × sale price. For dated flow analysis use inventory/movements. Purchase movements include only state-2 documents with a receiving store; their landed unit cost is line amount × cost rate ÷ quantity, with null for a zero denominator.

These are typical signs for normal positive source quantities, not positivity constraints. Adjustments retain their stored sign; depreciation is negated. Source data must be validated independently.

Document totals repeat on transfer, stock-adjustment and depreciation lines as well. Deduplicate by the document identity before aggregating header totals.

Transfers

A transfer exposes both sides: sourceMovementQty is −quantity and destinationMovementQty is +quantity. For a balanced transfer those movements cancel when aggregated across both stores.

Markdowns, promotions and coupons

  • markdownPercent is (1 - markdown price / original price) × 100, expressed in percentage points: 25 means 25%. It is null when the original price is missing or zero.
  • getValue carries the configured reward value. Interpret it with the promotion type and rule flags; it is not a universal percentage or monetary amount across all promotion types.
  • Promotion relationship endpoints expose the stores/items/client categories/tiers/cashback stores attached to the promotion.
  • Discount-coupon endpoints expose event metadata and store eligibility. Raw coupon codes/prefixes are intentionally not exposed.

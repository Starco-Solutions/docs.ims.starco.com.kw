Authentication & Access

Business API access is controlled by API key, client status/validity, company assignments and scopes.

API key header

X-IMS-API-Key: YOUR_API_KEY

The complete key is shown only when it is generated or rotated. Existing keys cannot be recovered. Store the key in an appropriate secret store rather than source code or configuration committed to version control.

Access checks

  1. The key must exist, be active, not revoked and not expired.
  2. The API client must be active and within its Valid From / Valid Until window.
  3. The requested company must be assigned to the client.
  4. The client must have the scope required by the endpoint.
  5. The client must remain within its minute/day request limits.

Customer access

Obtain explicit approval for customer data access and an API key assigned to the company with customers.read. Sales, Partner Data and other scopes do not grant Customers access. Ask your administrator to confirm that the endpoint is available for your company; see IMS Global API Administration.

Company confidentiality

At the company-access lookup, a caller without access receives the same 404 company_not_found response used when the company is unavailable. Scope and request-validation failures may occur before that lookup; not every unauthorized-company request reaches the 404 response.

Key lifecycle

Keys may be generated, rotated or revoked by authorized IMS administrators. Rotation creates a replacement key and invalidates the old key. Revocation is checked on subsequent authorization checks; revoked keys return 401 unauthorized.

Header and lifecycle details

Send exactly one X-IMS-API-Key header value. The middleware trims it and requires at least 20 characters before lookup; it does not offer Bearer authentication as an alternative. Key and client state are checked against the database on each request. Expiry and Valid Until must be in the future; Valid From must not be in the future.

Stored keys use SHA-256 hashes, with only metadata and prefixes returned in key listings. Rotation inserts the replacement and revokes the old key in one transaction, with no grace period. It does not cancel already-running requests.

The access checks above are requirements, not an execution-order guarantee: quota enforcement precedes endpoint scope/validation and company access.

Ordinary Business API contract policies

Every ordinary external Business API request requires an active company assignment and a configured company contract, in addition to its scope. Supplier and store lists restrict rows differently for different resources: use the policy paragraph for the specific endpoint. A filter never expands authorization. An empty supplier or store list does not mean unrestricted access.

Items and suppliers use supplier membership; inventory uses both supplier and store membership; purchases use supplier and purchase-center membership; transfers use supplier membership and either source or destination store. Stores, sales and footfall use store membership. Movements, adjustments, depreciations and markdowns use item-supplier membership. Customers and Customer Delta are company-wide personal-data resources, requiring their separate customers.read scope and a configured ordinary contract. Promotion/coupon relationships retain their parent eligibility rules and authorized related rows.

Financial permission controls specific cost and rent fields, not every monetary value: retail prices and sales values can remain visible. The endpoint reference identifies every nullable masked field. External transfer, adjustment and depreciation document totals remain null even with financial permission because an authorized line subset may not represent the whole document.

Trusted-internal clients bypass ordinary contract row restrictions and financial masking. They still need valid key/client state, scope and company access. This is an administrator-controlled client status, not a query parameter or a privilege a partner can request in its HTTP call. Partner Data always follows its separate active company policy; trusted-internal status is not a replacement for it.

Hypothetical contract comparison

Company 1 has item DEMO-SHIRT-M from supplier 7 in stores 101 and 102. Contract A authorizes supplier 7, store 101 and no financial data; its inventory request returns only store 101 for this item, with unitCost and stockValue null. Contract B authorizes supplier 7, stores 101 and 102 and financial data; the same request can return both stores and their permitted costs. Both contracts can see currentRetailPrice. A Partner Data client instead receives its policy-derived availableQty and retail fields, never these ordinary cost fields.

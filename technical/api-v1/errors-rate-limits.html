Errors & Rate Limits

Use status codes to distinguish authentication, authorization, validation, throttling and service failures. Parse error bodies defensively because validation and unexpected errors can have different shapes.

Common responses

StatusErrorMeaning
400invalid_company, invalid_page, invalid_page_size, date_range_required, invalid_date_range and endpoint-specific validation codesThe request is authenticated but invalid. Correct the request before retrying.
401unauthorizedAPI key is invalid or inactive (including revoked/expired key behavior).
403forbiddenThe client is valid but does not have the required scope.
404company_not_foundThe company is unavailable or the client is not authorized for it.
429rate_limit_exceededThe client exceeded its configured minute or daily request limit.

Endpoint-specific 400 codes include invalid_transaction_type, invalid_document_state, invalid_movement_type, invalid_promotion_type, invalid_promotion, invalid_expiry_range and invalid_coupon_event. Partner Data adds its policy and cursor errors, including contract-unavailable 503.

Rate-limit response

{
  "error": "rate_limit_exceeded",
  "message": "The API client has exceeded its minute request limit.",
  "retryAfterSeconds": 60
}

When throttled, wait for the supplied retry period and honor the HTTP Retry-After header. Do not continuously retry a 429 response.

Validation examples

{
  "error": "forbidden",
  "message": "The API client does not have the inventory.read scope."
}
{
  "error": "company_not_found",
  "message": "The company does not exist or this API client does not have access to it."
}

Error-shape boundaries

The examples above show explicit controller/middleware responses. ASP.NET model-binding validation can return a different validation envelope, so do not require every 400 to have error/message. Unexpected errors may return 500 without the illustrated error/message envelope. Scope/validation failures can precede company lookup.

Quota windows and multiple instances

Limits use fixed UTC calendar-minute and calendar-day windows, shared by a client's keys. Daily quota is checked before minute quota. Counters are held in the API process: restart/redeployment resets them, and independently running instances have independent counters. These counters are not a distributed deployment-wide quota. Request limits are configured per client; no universal requests-per-minute value applies.

Quota accounting happens after successful key authentication but before endpoint scope, company and query validation. Authenticated rejected requests can consume budget. Missing or invalid keys do not consume this quota. The sample 60-second retry is illustrative; use the actual response value.

Request logging

Throttled calls and authenticated downstream attempts are logged by this middleware; requests rejected for missing/invalid keys return before its request-log write. Logging failures produce a warning without replacing the primary response. Do not interpret this as complete infrastructure access logging.

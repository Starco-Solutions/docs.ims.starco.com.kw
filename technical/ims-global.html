IMS Global

This guide applies to IMS Global 1.7.0.0 and IMS API 1.1.0.0. Confirm the installed software and database migrations for your environment before using these workflows.

Central IMS administration for companies and database provisioning, global users/company access, Business API clients/keys, workstations, cross-company tools and system version control.

Administration boundaryIMS Global is a separate administration application. It is not the screen used for normal company transactions or company-local operational permissions.

Access and Security Guard

IMS Global validates the workstation through IMS.Api, authenticates the global user, enforces required password changes and then requests a Global Administrator session. The main window identifies the session as Global Administrator • Security Guard. Each administration module revalidates the session before opening. The session token is held in process memory; local token presence alone does not establish current authorization or expiry. The configured API URL requires HTTPS outside localhost.

Main window and menu reference

The main window is titled IMS Global Administration. The Administration area contains six module buttons; the System menu contains workstation, version, HA and exit commands. The Operations Log is a panel in the main window.

Operations Log

The main-window panel displays administration information, success, warning and error messages for the current IMS Global session. Review the relevant operation messages before proceeding after a reported failure. API Request Log and Admin Audit are separate views in API Administration.

System → Exit

Choose System → Exit to close the IMS Global main window.

Companies and database profiles

The Companies screen stores Company Code, Company Name, Country Code, Calling Code, Currency Code, Time Zone and active status. The database profile contains Description, Host / Server, Port, Database Name, Username, Database Password, SSL Mode and Database Active.

The saved database password is not repopulated into the password field. The screen shows whether a password is already stored; leaving the field blank retains the current secret when editing an existing profile.

Create a company database

Prerequisites: the installation includes the consolidated IMS_DB_Create.sql company schema, including the Business API, Customer Catalog, Partner Data and Partner Stock Delta contracts. The PostgreSQL server must already have an isolated ims_api LOGIN role with no elevated privileges or membership in other roles. The company application username must be separate from ims_api and ims_service. Server preparation is separate from company provisioning.

  1. Create or select the company and complete its database profile.
  2. Enter the intended company database password.
  3. Click Create DB.
  4. Confirm the company, Database and target Server.
  5. Enter PostgreSQL administrator credentials when IMS Global prompts for them.
  6. Wait for the Create Company Database operation to complete.

IMS Global creates and initializes the company database. Database creation is an IMS Global administration task, not a manual PostgreSQL setup procedure. After the operation succeeds, the company database password is secured through IMS.Api.

The stages save company metadata, obtain API provisioning details, create the database, apply the consolidated schema, configure the company role, initialize data and the API-supplied administrator, then validate the 28 API contract views, Customer Catalog, Customer Delta, Footfall, Partner Stock Delta and read-only API access. The reserved built-in administrator is initialized with Administrators policy 1. The company runtime password is secured through IMS.Api after successful provisioning.

Existing databases need a separate upgrade. Create DB provisions new companies; installing a newer IMS Global does not automatically migrate existing company databases. Existing companies need a separately approved migration to the required company contracts, including the Customer Catalog view. The consolidated new-company schema is not an existing-company upgrade procedure. Verify the company contracts and read-only API access before granting access. Treat scope-catalog setup and client authorization as separate steps: confirm an explicit customers.read grant and company assignment for each approved client.

Staged operationIf provisioning reports an error, preserve the operation log and have an authorized administrator check the completed database, initialization and password-storage stages before retrying. Create DB rejects an existing database. Do not drop/recreate it as a routine retry.
Use IMS GlobalDo not create, clone or initialize a company database manually. The supported workflow is IMS Global → Companies → Create DB.

Change a company database login or password

The Company database profile keeps the IMS Client database login separate from the stored password. A saved password is never repopulated into the password field; leave the field blank to keep the current secret.

When an administrator changes the database password for an existing company, IMS Global prompts for a privileged PostgreSQL account. IMS Global uses that temporary privileged session to change the operational IMS Client role, validates the new login and only then asks IMS.Api to secure the updated password in the company profile.

If the database Username is changed, IMS Global again requests a privileged PostgreSQL account. The target login role is created when missing (or reused when it already exists), configured with the permissions required by the IMS Client, validated against the company database and then saved into the company profile.

Privileged PostgreSQL credentials are temporaryThe administrator credentials entered in the prompt are used for the current role/database operation. They are not the company runtime login and are not stored as the company database password.

Changing Username requires a password. Roles are cluster-wide: profiles sharing host, port and role can be affected by the same password change. IMS Global warns and attempts to update matching profiles. Review any reported profile-save or secret-update failure and verify the affected connections before reconnecting clients. Newly created roles deny elevated PostgreSQL privileges; reusing a role does not strip its previous privileges or memberships.

API Administration

Use API Administration to manage External Business API clients, permitted companies and scopes, request limits, Partner Data policies and API keys. The API Administration guide covers the Dashboard, Clients, Companies & Scopes, Partner Data, API Keys, Request Log and Admin Audit workflows for Global Administrators.

Grant only the companies and scopes an integration needs. customers.read is an independent grant: Partner Data access and unrelated read scopes do not authorize customer access. For the consumer-facing contract, see the Business API v1 developer guide.

Global Users and company access

The Users screen maintains Login Name, User Name, Email, Cell Phone, Disabled state, password-reset state and Global Administrator status. A user must have at least one company, and exactly one company is marked Default. Company rows separately record whether the user has access and whether that company is the default.

Saving updates the global identity/company assignment through IMS.Api, then synchronizes local profiles to assigned company databases. If the operation reports a company synchronization failure, review the saved global assignment, resolve the named company issue and verify its local profile before relying on the change.

Each company owns its policy definitions and effective permissions. During user synchronization, existing destination-company memberships are preserved. Additional memberships are copied from the Default company only when both the numeric policy ID and trimmed, case-insensitive name match. Policy 1 is not copied as an ordinary membership, and a missing match does not grant an ordinary user Administrators access. The reserved built-in administrator receives Administrators policy 1.

New company access requires a policy checkAfter saving newly assigned company access, IMS Global lists the affected companies and databases. Before the user starts IMS Client there, sign in to each target database and verify an appropriate company-local policy. Assign one manually if none was synchronized. Company access alone does not assign permissions.

Review effective permissions in each destination company after synchronization. Matching policy names and IDs do not guarantee that the permissions inside those policies are identical. Company-local Store, Supplier, transfer and transaction rights remain in System → Users Accounts.

Built-in administrator

The reserved built-in administrator cannot be renamed, disabled or stripped of required Global Administrator authority. Existing active-company access is protected; company administration ensures this identity has company access. Use separate named administrator accounts for day-to-day administration and review their access explicitly.

Self-protectionThe account currently running IMS Global cannot remove its own Global Administrator access, disable itself or reset its own password from Global Users.

System → Workstations

Open System → Workstations. The Workstations administration screen lists registered workstation identity, machine name, authorization state, first/last seen times, fingerprint-change time, hardware fingerprint and notes. Authorized workstations can be blocked and blocked workstations can be approved. The workstation currently running IMS Global cannot block itself.

System → System Version

Open System → System Version to maintain the global IMS Assembly Version, Loader Version and Critical-update flag through IMS.Api.

Cross-company setup tools

Clone Policies is intended for reusing selected Group Policy definitions across companies without manually rebuilding every permission set. Clone Suppliers can reuse Supplier/Brand setup and, when selected, related item master data. These are controlled setup tools; they are not a mechanism for cloning an entire company database.

Clone Supplier and Sync Items Master

Use Clone Suppliers for a selected source-to-target setup. Choose different source and target companies, select the supplier, decide whether to include Items Master Data, and confirm the company and supplier names. Supplier and brand setup is copied or matched; the optional item operation also brings the required merchandise dependencies, missing IMS pictures and secondary barcodes. Existing matching items are reused. New items start with original and current retail prices of zero and item state 0; review regional pricing before selling them.

Open Sync Items Master from Clone Supplier to fill gaps for one supplier across all active companies with active database profiles. At least two are required. This is a shared catalog operation, not a stock-transfer, transaction-copy or price-update operation.

  1. Select one supplier from the combined supplier list and a Priority Company. Supplier IDs must identify the same supplier across companies.
  2. Choose Preview. Preview reads the catalogs without changing them and reports missing items, missing additional barcodes and items needing a source outside the priority company.
  3. Review every company in the log. Resolve incompatible table layouts, supplier-name/ID conflicts, product-number versus style/color/size conflicts, barcode ownership conflicts, or missing brand, category-parent and statistical-period dependencies in the named source.
  4. Choose Sync and confirm the supplier, priority and totals. The application rebuilds the plan before writing; if catalogs changed, run Preview again.
  5. Review the per-company results, set regional prices and item state for newly created items, and run Preview again to confirm the remaining work.
DataSynchronization rule
Source selectionFor each product number, use the priority company if it contains that item. Otherwise use the first available company in company-ID order. The priority company may itself receive missing items from another company.
Existing destination itemsPreserve existing item values, including local prices, state and main barcode. Add missing additional barcodes after checking ownership.
New destination itemsCopy the chosen source item and required supplier, brand, category and statistical-period data, matching dependencies to the destination. Original/current retail prices become zero and state becomes 0.
IMS themes and picturesIMS item attributes such as Theme are copied for new items. A missing IMS picture for the style/color is copied when inserting a new item; existing destination pictures are preserved. This is not a refresh of pictures for already-existing items.
Shopify-specific dataSync Items Master leaves online enablement, quantity reduction, handle, web color, online original/current prices and delta timestamp to destination defaults for new items. Configure that company's online data separately.
Additional barcodesUse the combined barcode set from the participating companies. A barcode cannot be associated with different items. An existing destination main barcode remains the main barcode.

Hypothetical example: Company Cedar and Company Dune share supplier 70. Cedar is the priority company and has item A; Dune has item B. Preview proposes A for Dune and B for Cedar. If Dune also knows an additional barcode for A, it can be added in Cedar. Existing A in Cedar keeps its regional price; newly inserted A in Dune starts at zero retail price and state 0. Dune's Shopify values are configured locally. If the same barcode belongs to B in either company, resolve the conflict before syncing.

A stopped synchronization can leave completed companies saved. Correct the reported issue, Preview again and rerun: already-present items and barcodes are recognized. Do not delete valid destination items to force a rerun.

Services: scheduling and company authorization

Open Services, select the company, choose Autos or Shopify, and select an existing service identity. Refresh loads the current company flags, identities and grants. Identity choices are scoped by their service grants; an unassigned identity's first grant assigns it to the chosen service.

  • Enable Autos / Disable Autos changes that company's scheduling flag. Disabling prevents future Autos scheduling; a current cycle may finish. Credentials and history are retained. Enabling still requires valid service authorization and configured job schedules.
  • Grant Company Access / Revoke Company Access controls the selected identity's access to the selected company for the selected service. Confirm the names before saving. This does not change credentials, the other service or Autos Enabled.
  • Shopify uses separate grants and its application/profile Start/Stop controls. There is no Shopify enable flag in this screen.

These controls administer existing identities and grants. They are not general-purpose editors for service bearer credentials. See service administration for the Windows service and Shopify desktop requirements, bootstrap and operator checks.

Generate Recovery Package

Generate Recovery Package creates one installer for Autos and Shopify. The Global installation needs the approved application ZIPs, recovery installer assets and Windows IExpress. Generation also requires a Windows ProgramData path without spaces. Global must be connected to the intended HTTPS API origin; that origin must be reachable from the replacement host. A localhost origin refers to the replacement host itself and cannot address an API on a different machine. Exactly one active Autos identity and one distinct active Shopify identity with the appropriate active company grants must be identifiable. Review grants if generation reports ambiguous or missing identities.

  1. Isolate the previous Services machine so it cannot run duplicate work. Confirm the replacement with the responsible administrator.
  2. Choose Generate Recovery Package and verify the displayed Autos identity, Shopify identity and API origin.
  3. Confirm generation. The installer is saved on the desktop with a displayed expiry. It contains a single-use enrollment ticket valid for 30 minutes; it does not embed a service bearer token or company database password. Protect the installer as an enrollment credential.
  4. On the replacement Windows machine, launch the generated IMS-Services-Recovery-…exe as the intended Shopify desktop user and approve elevation under that same account. The installer checks the .NET 10 Desktop Runtime and payloads, then redeems the ticket over HTTPS, installs the protected credentials, starts Autos and creates the Shopify shortcut.
  5. Open Shopify, check its company profiles and RunOnStartup settings, and verify business activity for both applications. Arrange authorized retirement of old host credentials after verification; enrollment itself does not revoke them.

The ticket cannot be reused after enrollment, and new enrollment credentials expire after 30 days. If a ticket expires, generate a fresh package. If installation reports a failure after enrollment, preserve the reported installation phase and have an administrator inspect the machine before generating another package. Do not interpret a failed installation as proof that enrollment did not occur. Review the replacement-machine prerequisites and connection settings before installation. Recovery Package administration is distinct from database backup/restore and vault encryption-key recovery.

System → HA Health

HA means High Availability. Open System → HA Health in IMS Global for a read-only observation of the PostgreSQL cluster. Choose Refresh to retrieve a new observation. The screen shows the primary, connected endpoint, streaming/expected/missing standby counts, observation time in workstation local time, and node ID/name, registered role and active state, replication state, synchronization state, replay lag and lag bytes. Empty lag fields mean no value was reported; they are not a measured zero.

The authorized IMS API service reads repmgr registration and the live replication snapshot. Workstations do not connect directly to that monitoring database or receive its credentials. Registered active state is metadata; streaming state is observed at refresh time.

  • Healthy: the connected endpoint is not a standby, exactly one active primary is registered, at least one standby is expected, and every expected standby is observed streaming.
  • Degraded: those conditions are not all satisfied. A connection to a standby explicitly leaves primary health unconfirmed. Review node states and escalate to the database administrator; the displayed health classification does not apply a numeric lag threshold.
  • Unknown / unavailable: the observation failed. Check the API connection and authorized monitoring configuration, then Refresh. It is not confirmation that the cluster has failed.

This screen cannot promote a standby, perform failover, manage PostgreSQL services or execute Linux administration. Use the approved database operations procedures for those tasks. Client workstation/session monitoring remains in the IMS Client System Dashboard.

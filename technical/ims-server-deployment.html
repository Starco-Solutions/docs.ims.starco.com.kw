IMS Server Deployment

Install a new IMS API and Global database, or restore service around approved database backups. Use IMS Global separately to create company databases and administer access.

Choose the correct operationFresh Installation creates a new Global database. Disaster Recovery uses an already restored Global database; it does not restore backups, import the packaged schema or migrate company databases. Neither mode is a routine API binary-update procedure.

Prepare the server and offline package

  • Use a Windows x64 server running Windows Server 2019 or newer and a Windows administrator account. Plan CPU, memory and storage for the actual workstation, API, reporting and service workload; the installer's recommendations are sizing guidance, not a universal hardware minimum.
  • Make the Windows component payload available locally for IIS Web Server, IIS Management Console and IIS Management Scripts and Tools. Setup uses offline component installation, not network downloads.
  • The API requires .NET 10.0.14 or a compatible later .NET 10 patch, its ASP.NET Core runtime and IIS Hosting Bundle integration. The offline package contains the 10.0.14 Hosting Bundle. Setup preserves newer compatible installations; repair an incomplete newer bundle with matching offline media.
  • Provide PostgreSQL 18.3 or a later 18.x minor release. Older releases and future major versions are not accepted by this installer. Setup checks the actual server version and does not install or upgrade PostgreSQL.
  • Prepare the API DNS name, HTTPS port, a new empty deployment directory and dedicated IIS site/application-pool names. Install a trusted matching certificate with a private key and Server Authentication usage in Local Computer → Personal. Temporary self-signed certificates are limited to testing/recovery validation and are not production-ready.
  • Provide PostgreSQL connection details and a separate administrative login authorized for database/role provisioning. Use trusted PostgreSQL TLS; VerifyFull is the default and requires a matching certificate name.

Keep these six approved package files together: Setup.exe, IMS.Api.zip, IMS_Global_Schema.sql, dotnet-hosting-10.0.14-win.exe, manifest.json and README-DR.md. Use Setup.exe --validate-package <folder> to check package integrity. Verify the package's trusted release origin separately; a matching file hash alone is not approval to install an unknown package.

The Global schema is structure-only. Do not add production users, company records, passwords, vault data or seed SQL. Fresh initialization uses the approved Bootstrap:FreshInstallation values in the packaged API configuration: Client assembly/file versions, Global version, Updater version and Client critical-update flag. These published versions are distinct from minimum login-version settings.

PostgreSQL recommendations

Open PostgreSQL recommendations… in the installer sidebar. Review Workload assumptions, Network access and Configuration preview. Enter workstation/session demand, API pool demand, background services, reporting concurrency and administrative reserve. Use Calculate / reset values, review the proposed values, then Preview configuration. Export report… saves a new recommendation document without overwriting an existing file.

Use independently verified custom networks for a remote PostgreSQL host; detected adapters belong to the installer machine. Preview/export does not change PostgreSQL configuration, firewall rules, services or an HA cluster. A DBA must review and apply any approved recommendations separately.

Fresh Installation

  1. Run Setup.exe as a Windows administrator. In Installation mode, choose Fresh Installation. Select Continue after each input.
  2. Enter API DNS host name (certificate name, without scheme), choose Existing trusted certificate, then supply Dedicated IIS site name, Dedicated IIS pool name, New API deployment directory and HTTPS port.
  3. For the first empty Global database, leave Configure IMS Update Server at Skip (normal API installation only). Complete first-workstation approval below, then configure updates separately.
  4. Review prerequisite checks. Approve missing offline Windows/IIS and Hosting Bundle installation only after reviewing the prompt. If Setup requests a restart, restart under the maintenance procedure and rerun Setup normally. No database passwords or encryption keys have been collected at this point.
  5. Enter PostgreSQL host or IP, PostgreSQL port, Global database name, PostgreSQL SSL mode and PostgreSQL administrative username, followed by the administrative password. Setup refuses Fresh if either the reserved ims_global database or the requested database already exists.
  6. Enter and confirm New System Admin password (login administrator). Use 8–128 characters with uppercase, lowercase, a digit and a symbol.
  7. Supply passwords for the separate ims_service and ims_api runtime roles. Manually entered role passwords require 16–128 printable ASCII characters without spaces, including uppercase, lowercase and digits. For nodes sharing a PostgreSQL role, enter the same securely held password on every node rather than generating a different password on each.
  8. Approve new installation encryption-key generation. Securely record the one-time key IDs and values in approved custody. Keep them out of screenshots, recordings, reports and logs.
  9. Review the exact database, IIS path, HTTPS target and published version values. Approve Apply this deployment plan? only when they are correct. Approval is separate from prerequisite installation.
  10. Wait for database initialization, runtime-role checks, API deployment and HTTPS health verification. Setup creates the Global schema, initial API scope catalog, system-version record and System Admin account with login administrator. Scope registration does not grant an external API client access.
Preserve partial resultsCancellation or failure does not undo completed stages. If Fresh created a database before initialization failed, do not delete it or rerun Fresh against it. Have the DBA inspect it and select an approved recovery procedure.

Approve the first administration workstation

New workstation registrations remain pending. Run IMS Global on the intended administration machine and attempt its normal connection once to register it. This does not grant a Global Administrator session or update access.

  1. If an authorized Global Administrator is already available, use IMS Global → System → Workstations to review and approve the intended device.
  2. For the genuinely first administration workstation, an authorized DBA must independently verify its 32-character workstation ID and 64-character hardware fingerprint against the intended machine.
  3. In the independently verified Global database, review that existing pending public.workstations row. Approve only the row matching both the reviewed ID and fingerprint and currently having is_authorized = false. Require exactly that row before committing the approval; otherwise roll back. Do not insert guessed records, approve all rows or change registration defaults.
  4. Retry IMS Global sign-in as administrator using the password set during installation. Use the normal Workstations screen for subsequent approvals.

See workstation administration for routine approval and blocking. Workstation approval is separate from user authentication and company permissions.

Create the first company and connect IMS Client

  1. In IMS Global, open Companies. Register the company and its database profile using the intended PostgreSQL destination, separate company runtime username and password.
  2. Choose Create DB, review the company/database/server, and supply PostgreSQL administrator credentials when prompted. Follow Create a company database; do not initialize it manually.
  3. Review user company assignments and company-local policies. Company access alone does not grant operational permissions.
  4. Configure IMS Client for the intended HTTPS API. Register and approve its workstation, sign in, and select an authorized company when prompted. Confirm that the expected company opens before performing business work.
  5. Review the workstation inventory, then follow IMS Update Server administration if authorized updates are required.

Runtime roles and protected credentials

ims_service is the API's Global runtime login; ims_api is the separate business API database login. Company IMS Client logins are provisioned through IMS Global. PostgreSQL administrator credentials entered into Setup are temporary, not runtime credentials. Existing runtime-role passwords are preserved unless the operator explicitly approves a cluster-wide replacement. Unsafe elevated or overprivileged roles require DBA review.

Setup stores runtime credentials and encryption keys in the machine-protected %ProgramData%\IMS\API\runtime-secrets.bin, outside the application directory. Access is restricted to SYSTEM, local Administrators and the dedicated API application pool. The fixed store supports one managed API installation per Windows node. Do not copy it to another machine as a recovery-key backup.

Disaster Recovery

Isolate before connectingBlock the recovery server, API and operator workstation from production PostgreSQL networks. Restored company mappings can still point to production. Setup does not rewrite those mappings or enforce network isolation. Keep the block until every mapping has been reviewed.
  1. Prepare the replacement Windows server, offline package and trusted HTTPS certificate as above. Have the DBA restore approved Global and company database backups through the organization's backup procedure. Confirm the recovery destinations independently.
  2. Run Setup and choose Disaster Recovery. Use a new empty deployment directory and dedicated IIS resources. Complete prerequisite checks/restarts before supplying secrets.
  3. Confirm recovery isolation and enter the verified Global PostgreSQL target and administrative credentials. Setup validates the restored schema and initialization records; it does not import the packaged Fresh schema or perform business database migrations.
  4. Supply the existing runtime-role passwords. Do not approve a password reset unless its effects on all nodes using that cluster-wide role have been reviewed.
  5. Choose Existing keys available. Enter the original company-password key ID/value, all required recovered vault key ID/value pairs and the exact active vault ID. Keep recovered IDs unchanged. See key preservation.
  6. Review and approve the deployment plan. Setup configures and validates Global runtime access.
  7. Company database action defaults to Skip company database configuration (default). To verify a company, choose Select an independently verified recovery database target and enter its recovery IP, port, database and SSL mode. Choose Connection check only or separately approve Configure ims_api permissions. Type the exact displayed operation-specific confirmation. Permission changes and an existing role-password reset require separate approval. VerifyFull against an IP requires that IP in the PostgreSQL certificate.
  8. Wait for API deployment and /health/live and /health/ready verification. Readiness checks Global connectivity, not every company, vault record or business endpoint.
  9. Point IMS Global to the recovery API. Check both IMSApiUrl and any overriding IMS_API_URL environment setting. Authenticate from an approved workstation.
  10. Open Companies, select each restored profile and change Host / Server, Port, Database Name and SSL Mode to the verified recovery destination. Preserve Username and leave Database Password blank to retain the existing encrypted password. Choose Save and reselect to verify the mapping. Do not choose Create DB for a restored database.
  11. After mappings and isolation are verified, check company runtime access, IMS Client login, authorized business API reads and required integrations. Return services to operation only after the responsible administrator approves the recovery result, trusted TLS and service coordination.

Saving a mapping does not verify the destination connection or configure ims_api grants. Entering a password or changing Username invokes a separate PostgreSQL administrator operation against the newly entered target and can affect other profiles sharing the same role. Review the target before making either change.

Preserve encryption keys

Company database passwords use one active company key; retain its original ID and value to decrypt restored passwords. Secret Vault supports multiple recovered keys and an active ID; preserve all keys still needed by stored records. Adding a new active vault key does not migrate existing ciphertext.

For two API nodes, enter the same appropriate keys and shared role passwords on each node through Setup. Each node creates its own local protected store. Machine-bound protected files are not portable key escrow.

Existing keys lost generates new keys only after an explicit warning and approval. It leaves encrypted database records intact, but new keys cannot decrypt them. Recover company database passwords through the authorized IMS Global password-replacement flow first; replace other affected integration/service passwords through their approved IMS settings. Never delete vault records to bypass a decryption failure.

Verification and interrupted installation

  • Confirm trusted HTTPS, both API health routes, an approved management workstation and successful Global Administrator login.
  • Confirm version information, initial user and scope catalog for Fresh; verify each required company and retained credential for recovery.
  • Test IMS Client access and the business/services actually required by the installation. A successful Setup exit does not replace these checks.
  • For an Update Server-only failure, preserve the working API/database and retry Setup.exe --configure-updates. Do not reset database roles or keys.
  • For a partially created API/IIS installation, preserve the protected store and exact resources, then follow the package's controlled retry procedure with an authorized administrator. Do not remove unrelated sites, pools or certificates.

Exit codes: 0 selected operation completed; 1 failed stage; 2 cancellation or invalid usage; 4 API deployed but company verification incomplete; 5 API deployed but optional updates need follow-up; 3010 restart required before retry. Skipped company checks leave company access unverified even if the operation returns success.

IMS Architecture

Roles and boundaries of IMS Client, IMS Global, IMS API, IMS Autos and IMS Shopify, with separate global administration and company operational databases.

Core components

Applications and services

ApplicationRole and detailed guide
IMS Client 9.4.6Windows operational application for Sales, Inventory, Purchasing, Finance, Reports and company administration. See the IMS Client main screen.
IMS Global 1.7.0Administration application for companies and database profiles, Global users and company access, workstations, versions, API contracts and service authorization. See IMS Global.
IMS API 1.1.0Central service with two distinct responsibilities: internal IMS Security Guard & Secure Bootstrap, authentication, Global administration and protected-secret access; and the external Business API, where authorized integrations read company data under scopes and contract policies. See IMS API administration.
IMS Autos 9.2.NET 10 Windows service that schedules company business processes independently using each company's time zone. See Autos processes and activity and service administration.
IMS Shopify 4.4.0.NET 10 Windows desktop integration application with independent company/profile workers for Shopify operations. See Shopify Integration Server. It uses its own service identity and company grants, separate from Autos.

Databases

DatabaseResponsibility
ims_globalPostgreSQL global administration database containing Global identities, company access, workstation and version records, API administration and protected-secret data.
Company databasesSeparate PostgreSQL operational databases containing each company's configuration, stores, inventory, transactions, finance and history. See Multi-Company Architecture.

Session flow

  1. The workstation is validated.
  2. The user authenticates against the global IMS identity.
  3. IMS resolves active company access.
  4. The default/selected company determines the company database runtime profile.
  5. The client opens the company operational context and then applies company-local permissions.
Separation by designGlobal identity and company membership are centralized, while operational data and local authorization remain company-specific.

Runtime and version boundaries

The authorized IMS client receives a company runtime profile and connects directly to PostgreSQL; the API does not proxy all operational SQL. Secret storage at rest, API authorization and client runtime exposure are separate boundaries. Autos and Shopify have separate service/company grants and protected host credentials. Autos Enabled controls scheduling; it does not replace authorization. Shopify also requires each store profile’s App Token. See service administration. A stored-secret indicator is not a successful connection test.
